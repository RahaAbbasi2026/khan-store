# انتشار نسخه تجمیعی اصلاحات امنیتی

این راهنما جایگزین راهنماهای انتشار قبلی است. از دو فایل زیر استفاده کنید:

- `khan-store-backend-security-complete.zip`
- `khan-store-frontend-security-complete.zip`

هر فایل، کل کد همان بخش و تمام تغییرات قبلی فروشگاه را دارد. فایل‌های latest کپی همین نسخه‌ها هستند.

## تفاوت مهم با بسته‌های قبلی: migration لازم است

این نسخه به ستون‌های نسخه سبد و وضعیت شروع پرداخت، کلید یکتای checkout و جدول‌های کپچا و محدودیت درخواست نیاز دارد. تغییرها افزایشی‌اند؛ SQL آن‌ها در `prisma/migrations/20261022010000_security_state/migration.sql` است. شروع برنامه دیگر هیچ `db push`، reset یا پذیرش حذف داده انجام نمی‌دهد.

**صرفاً آپلود ZIP بدون اجرای migration کافی نیست.** دستورهای دیتابیس زیر را فقط در پوشه بک‌اند نسخه جدید و با DATABASE_URL همان دیتابیس فروشگاه اجرا کنید. اطلاعات واقعی اتصال را در چت یا فایل ZIP نگذارید.

### ترتیب انتشار برای دیتابیس فعلی فروشگاه

۱. از دیتابیس بکاپ قابل بازیابی تهیه کنید. تنظیمات واقعی اپ‌ها و نسخه فعلی را نگه دارید. پرداخت‌های جاری را بررسی و زمان کم‌ترافیک انتخاب کنید. پیش از تغییر schema و تا پایان به‌روزرسانی هر دو اپ، پذیرش سفارش جدید را با `SHOP_ENABLED=false` در بک‌اند متوقف کنید؛ callbackهای پرداخت را مسدود نکنید.

۲. Node.js هر دو اپ را روی 22 یا 24 قرار دهید و بسته بک‌اند جدید را برای انتشار آماده کنید. وقتی فایل‌های این نسخه در محیط اجرای دستور/کنسول در دسترس هستند، پیش از باز کردن ترافیک عمومی، مراحل ۳ و ۴ را اجرا کنید. اگر دسترسی کنسول نسخه جدید قبل از انتشار ندارید، migration را با همین کد از محیط مدیریتی مجاز متصل به دیتابیس اجرا کنید؛ این مرحله را حذف نکنید.

۳. چون نسخه‌های قبلی با `db push` ساخته شده‌اند، برای دیتابیس موجود ابتدا اجرا کنید:

```sh
npm run db:baseline
```

این دستور schema واقعی را با نسخه قبل از اصلاح مقایسه می‌کند و فقط در صورت تطبیق، baseline را در تاریخچه migration ثبت می‌کند. baseline روی دیتابیس دارای داده دوباره اجرا نمی‌شود. اگر تاریخچه متفاوت، drift یا خطا دیدید، **متوقف شوید و schema/history را تطبیق دهید**؛ از reset، حذف جدول، `--accept-data-loss` یا علامت‌گذاری کورکورانه migration استفاده نکنید. اگر baseline قبلاً ثبت شده باشد، دستور فقط پیام می‌دهد.

۴. سپس اجرا کنید:

```sh
npm run db:deploy
```

این فرمان migrationهای نسخه‌بندی‌شده را اعمال می‌کند. برای یک دیتابیس کاملاً خالی، مستقیماً همین دستور کافی است و baseline نباید به‌عنوان اجراشده علامت زده شود.

۵. بک‌اند جدید را با build و start موجود در package.json منتشر کنید و سپس ZIP فرانت‌اند را روی اپ فرانت‌اند بارگذاری کنید. بک‌اند با `npm run build` ساخته می‌شود و `npm start` یا `npm run start:prod` فایل `dist/src/main.js` را اجرا می‌کند. نیازی به ساخت جدول یا تغییر schema در start نیست. طبق مستندات لیارا، پلتفرم NodeJS اسکریپت build موجود را پیش از start اجرا می‌کند.

۶. تنظیمات موجود JWT، درگاه، دامنه‌ها و اتصال دیتابیس را حفظ کنید. `BACKEND_URL` باید آدرس عمومی HTTPS بک‌اند باشد تا URL تصاویر درست تولید شود. `NEXT_PUBLIC_API_URL` فرانت‌اند باید به همین بک‌اند قابل دسترس اشاره کند. `TRUST_PROXY_HOPS` به‌طور پیش‌فرض صفر است؛ مقدار 1 را فقط وقتی تنظیم کنید که اتصال مستقیم خارج از پراکسی معتبر لیارا ممکن نیست. در حالت صفر هدرهای IP ارسالی کاربر قابل اعتماد فرض نمی‌شوند، ولی کاربران پشت یک پراکسی ممکن است محدودیت مشترک بگیرند.

۷. بعد از کنترل سلامت هر دو اپ، `SHOP_ENABLED=true` و در صورت تغییر قبلی، `NEXT_PUBLIC_SHOP_ENABLED=true` را فعال و اپ‌های لازم را دوباره راه‌اندازی/بیلد کنید. ثبت‌نام، ورود، کپچا، افزودن کالا، دو بار کلیک checkout، پرداخت موفق/ناموفق، ادامه پرداخت و دریافت تصاویر را بررسی کنید. یک تراکنش واقعی کم‌مبلغ برای تأیید اتصال زرین‌پال لازم است؛ در این محیط پرداخت واقعی انجام نشده است.

## رفتارهای اصلاح‌شده

- کپچا دو دقیقه اعتبار دارد، تصادفی و یک‌بارمصرف است؛ پاسخ اشتباه هم آن را مصرف می‌کند. وضعیت در PostgreSQL مشترک است.
- محدودیت ورود/ثبت‌نام ۱۰ درخواست در دقیقه برای IP و حساب، تماس ۵، کپچا ۲۰ و سایر مسیرهای محافظت‌شده ۱۲۰ درخواست در دقیقه است. پاسخ عبور از سقف 429 و Retry-After دارد. این شمارنده‌ها بین نمونه‌های سرور مشترک‌اند.
- ثبت سفارش یک snapshot سبد، با کلید یکتا و تراکنش کوتاه، سفارش و درخواست پرداخت تکراری نمی‌سازد. درخواست بانک بیرون تراکنش دیتابیس است.
- سبد تا تأیید واقعی پرداخت حفظ می‌شود. «ادامه پرداخت سفارش» در حساب و رسید سفارشِ در انتظار پرداخت اضافه شده است. این گزینه مالکیت حساب را بررسی و همان Authority را دوباره استفاده می‌کند؛ مجوز رسید به‌تنهایی مجوز پرداخت نیست.
- پس از تأیید پرداخت، ثبت نتیجه و خالی کردن سبد یک تراکنش‌اند. اگر سبد بعد از checkout تغییر کرده باشد، به‌صورت خودکار پاک نمی‌شود تا اقلام جدید از دست نروند.
- کالاهای ناموجود در سرور رد می‌شوند؛ تعداد هر ردیف ۱ تا ۹۹، حداکثر ۵۰ ردیف و مبلغ سفارش حداکثر دو میلیارد تومان است. تاریخ تحویل از امروز تا ۳۰ روز آینده بر اساس زمان تهران و بازه تحویل مشخص پذیرفته می‌شود. تاریخ در API با قالب YYYY-MM-DD ذخیره می‌شود.
- سفارش‌های در انتظار پرداخت قدیمی با تاریخ متنی فارسی ممکن است برای ادامه پرداخت به پیگیری فروشگاه یا انتخاب دوباره زمان نیاز داشته باشند؛ تاریخ آن‌ها خودکار حدس زده یا بازنویسی نمی‌شود. سفارش‌ها و سوابق قدیمی حذف نشده‌اند.
- فهرست عمومی محصولات، مقاله‌ها، کارت‌ها و دیدگاه‌ها صفحه‌بندی و محدود شده است. کاتالوگ/سبد تصاویر را همراه Base64 بارگذاری نمی‌کنند؛ تصویر جداگانه از media endpoint دریافت می‌شود. تصویر فعلاً به‌صورت پایدار در همان PostgreSQL نگه داشته می‌شود، نه حافظه موقت سرور؛ انتقال به object storage/CDN برای مقیاس بزرگ‌تر یک بهینه‌سازی جداگانه است و برای این انتشار به حساب سرویس خارجی نیاز نیست.
- اطلاعات سفارش، شماره تماس، نشانی و شناسه داخلی مشتری یا سفارش در فهرست عمومی نظرات منتشر نمی‌شوند؛ نام نمایشی نویسنده نظر همچنان نمایش داده می‌شود.
- ذخیره تصویر جدید به PNG/JPEG/WebP/GIF معتبر تا ۳ مگابایت محدود شده؛ SVG پذیرفته نمی‌شود. JSON-LD محصول هم escape می‌شود تا متن محصول نتواند تگ script را ببندد.
- خطای موقت شبکه سبد جدید ایجاد نمی‌کند؛ افزودن زودهنگام یا ناموفق پیام موفقیت کاذب ندارد. عملیات سبد در مرورگر مرتب و خطاها نمایش داده می‌شوند.
- Next.js 16.4.2، NestJS 11.2.7 و Tailwind 4.3.3 با lockfile منتشر می‌شوند. CLI قدیمی Nest از مسیر ساخت حذف شده است. audit کامل هر دو بخش در زمان بررسی صفر هشدار گزارش کرده است؛ این نتیجه تضمین نبود تمام آسیب‌پذیری‌ها نیست.

## بررسی و محدودیت‌ها

آزمون‌ها شامل HTTP محلی، PostgreSQL تعبیه‌شده PGlite با Prisma واقعی، baseline و اجرای واقعی migrate deploy، rollback، رقابت درخواست‌ها، کپچا و rate limit، مالکیت سبد/سفارش و امنیت پرداخت هستند. PGlite یک محیط محلی تک‌اتصالی با multiplexer است و جایگزین تست فشار چند سرور روی PostgreSQL واقعی لیارا نیست.

بیلد و آزمون‌ها روی همین سیستم اجرا شده‌اند. دیتابیس واقعی، secretها، SSL، بکاپ و درگاه زنده لیارا از این محیط بررسی یا تغییر داده نشده‌اند. تصاویر و چیدمان در build و HTTP بررسی شده‌اند؛ بررسی بصری در مرورگر روی سایت منتشرشده همچنان لازم است.

## جایگزینی پس‌زمینه‌ی عکس محصول (پنل مدیریت)

- در فرم محصول پس از انتخاب عکس، یکی از پس‌زمینه‌های `public/backgrounds` را انتخاب کنید؛ پردازش کاملاً در مرورگر ادمین انجام می‌شود و تصویر نهایی ۱۶۰۰×۱۶۰۰ (JPEG زیر ۳ مگابایت) مثل هر عکس دیگری ذخیره می‌شود.
- بار اول، مرورگر مدل برش تصویر (حدود ۸۰ مگابایت) را از `staticimgly.com` دریافت می‌کند. اگر این آدرس از اینترنت شما در دسترس نبود، فایل‌های بسته‌ی `@imgly/background-removal-data@1.4.5` را روی هاست خودتان بگذارید و `NEXT_PUBLIC_BG_MODEL_URL` را روی آدرس آن (با `/` در انتها) تنظیم و فرانت را دوباره build کنید.
- کتابخانه‌ی `@imgly/background-removal` با مجوز AGPL-3.0 است؛ چون سورس پروژه عمومی است مشکلی ندارد، ولی اگر مخزن را خصوصی کردید، موضوع را بررسی کنید.
